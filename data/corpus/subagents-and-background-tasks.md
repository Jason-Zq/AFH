# 子代理与后台任务

## 为什么需要子代理

单 Agent 的上下文是稀缺资源。把子任务委派给子代理（Subagent），让它在**独立上下文**中执行、只把结论带回主线，一举解决三个问题：主上下文不被中间过程污染、子任务可并行、失败被隔离在局部。

## 任务委派模型

典型流程：

1. 主 Agent 分解任务，为每个子任务写清目标、边界与产出契约；
2. 运行时启动子代理，持有独立的对话历史与工具子集；
3. 子代理完成后返回结构化结论（而非全部过程）；
4. 主 Agent 汇总结论，继续推进。

委派的关键在"契约"：子代理不知道自己只是配角，目标描述必须自足——背景、验收标准、"不要做什么"都要写进任务书。

## 隔离上下文

隔离是双刃剑：子代理看不到主线历史，避免了污染，也丢失了背景。因此任务描述要显式传递必要上下文，而不是假设子代理"应该知道"。隔离同时意味着权限可以收窄：只读子代理不给写工具，缩小爆炸半径。

## 结果回收

- 回收的是**结论与证据引用**，不是过程轨迹；过程轨迹应落盘留档供调试；
- 子代理失败要有明确回报通道：部分结果 + 失败原因，而不是沉默；
- 并行子代理的结果按任务 ID 归并，避免张冠李戴。

## 后台任务

长任务（抓取、批处理）应作为后台任务异步执行：主 Agent 提交后立即继续工作，任务完成时以事件通知。这与子代理正交但常配合使用——子代理本身就可以在后台运行。

## MAF Harness 的 BackgroundAgents

Microsoft Agent Framework 的 Harness 形态内置了 BackgroundAgents 能力：以后台方式运行委派任务，带遥测与生命周期管理，主对话不被阻塞。其设计哲学与上文一致——委派显式化、上下文隔离、结果事件化回收——可视为该模式在工业框架中的标准实现。
