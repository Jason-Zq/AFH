# Agent 评估方法

## 为什么 Agent 难评估

传统 NLP 评估假设输出可比对（准确率、BLEU），但 Agent 的输出是多步轨迹：中间可能调用十几个工具、路径不唯一、殊途可以同归。评估 Agent 必须同时回答"结果对不对"和"过程好不好"两个问题。

## 结果评估与轨迹评估

- **结果评估**：只看最终产物——答案是否正确、文件是否改对、任务是否完成。可用精确匹配、单元测试、规则校验或人工核对。优点是客观，缺点是忽略效率与过程风险；
- **轨迹评估**：检查中间步骤——工具选择是否合理、是否走了弯路、是否有危险操作、是否重复无效调用。常用做法是把完整轨迹交给另一个模型或人工按量规（rubric）打分。

## LLM-as-Judge

用强模型充当裁判，按预设量规对结果或轨迹打分。优点是成本低、可大规模运行、能评估开放式输出；风险是裁判模型自身的偏见（偏好长答案、偏好特定风格），需要通过人工抽检校准、成对比较、交换顺序等方式缓解。

## 基准与回归测试

- **公开基准**：GAIA（面向通用助理的多步任务）、SWE-bench（真实 GitHub issue 修复）等，用于横向比较不同系统；
- **私有回归集**：从生产日志与失败案例中沉淀的自有测试集，每次改提示词、换模型、升级框架后全量重跑，防止"修好一个、退化一片"。这是工程上最有价值、也最被低估的一环。

## 实践要点

评估体系建议分层：离线回归集守门（每次变更必跑）、线上抽样人工评审（持续校准）、可观测性数据兜底（token、延迟、失败率趋势）。没有评估集驱动的提示词迭代，本质上是碰运气。
