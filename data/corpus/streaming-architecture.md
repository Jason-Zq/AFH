# 流式架构

## 为什么 Agent 必须流式

Agent 任务动辄数十秒到数分钟：多轮推理、多次工具调用。若等全部完成才返回，用户面对的是长时间无反馈的"黑盒"。流式把模型增量输出与中间事件实时推送，是 Agent 产品的体验底线。

## 推送通道

| 通道 | 特点 | 适用 |
|------|------|------|
| SSE | 单向、基于 HTTP、自带重连 | 服务端推模型增量，Web 端首选 |
| WebSocket | 全双工 | 需要客户端上行控制信号的交互场景 |
| SignalR | .NET 生态的实时抽象，自动降级（WebSocket→SSE→长轮询） | .NET 后端 + 多类型客户端 |

Agent 场景"服务端→客户端"是主流方向，SSE 通常够用；需要客户端随时打断、传回审批结果时，WebSocket 或 SignalR 更顺。

## 事件模型：不只是 token

成熟的 Agent 流不是裸 token 流，而是**类型化事件流**：思考增量、文本增量、工具调用开始/参数/结果、步骤边界、待办更新、错误、结束。前端按事件类型分别渲染——事件溯源式 UI：界面状态是事件序列折叠出来的结果，天然支持回放与调试。

## 背压

生产快于消费时必须反压，否则缓冲无限增长：

- 服务端按消费速度限速吐出事件；
- 客户端处理不过来时显式反馈（WebSocket 可下行控制消息；SSE 可借助连接层缓冲上限）；
- 对纯展示型 token 增量允许丢弃中间帧、只追最新状态。

## 取消

用户中途停止是常态而非异常：取消信号要贯穿 HTTP 连接、后台任务、模型调用三层，任何一层吞掉取消都会白烧 token。取消后应推送终态事件，让 UI 状态机干净落地，而不是悬在"运行中"。
